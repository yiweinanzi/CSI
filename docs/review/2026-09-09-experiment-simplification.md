# 实验流程精简建议

基于 main@1121a0e 的静态代码检查与仓库已保存的运行记录。未连接训练服务器，未运行新的训练或评估。本文件是改造方案，不代表改造已完成。

## 结论

当前系统同时承担定位研究、配对响应研究、风险校准、路径机制、独立引擎验证、环境供应链校验和自动论文主张裁决，超过两张核心结果表所需的范围。应新增轻量实验入口，逐步替换默认工作流，保留历史协议和结果以便复核。不能通过删除较强基线、不利数据、独立数据划分或更改历史 FAIL 来获得 SOTA。

## 已核实的困难来源

1. **评估任务过度捆绑。** `formal_evaluation_streaming.py::_fit_probe_bundle` 总是构建 compatibility、五组需要拟合的捷径探针以及 Response/四个变体；包含线性/MLP 候选后共 17 个拟合模型。12 个主 checkpoint 对应 204 次拟合。核心能力结果必须等待昂贵的附加对照。`_commit_probe_bundle` 在整组结束后才保存，`formal_probes.py` 的优化循环没有单探针的模型/优化器持久化恢复。
2. **2000 steps 实际是 2000 次全数据更新。** `formal_probes.py::_fit_binary` 在每次 optimizer.step 前遍历所有训练行；GPU 内存不足时仍保持全梯度累积。记录中的 38,696 行会产生约 7,739 万个样本处理次数/候选。把 batch 调小只改变内存需求，不减少总工作量。记录中 map-only linear 耗时 7056.739 秒。保留旧语义的加速与改变训练预算是两类改动，必须分开验证。
3. **大数组和重复特征物化。** `FormalDataset.load` 把完整 CSI、地图等读入 float64 数组；`formal_evaluation.py::_compatibility_dataset` 按样本拼接展平地图/CSI 的捷径特征并汇成数组。真实记录中代表性 C 的 RSS 峰值约 154 GB，D 的一次 RSS 观测约 242 GB。记录证明资源问题存在，但本次没有逐项测量这些分配对峰值的贡献。
4. **身份认证超出日常实验需要。** `evidence_context` 对非 fixture 调用运行环境认证；`formal_runtime_integrity.py` 扫描整个安装文件闭包，限制额外包、软链接、pyc 等。文件摘要有进程内缓存，不能说每次都完整重读所有字节，但目录扫描与严格环境耦合仍存在。`formal_run_approval.py` 还绑定外部 LLM 审批、随机 nonce、过期时间、prepared root 等。没有计时证据证明它们是最大的运行耗时，主要问题是维护和恢复成本。
5. **运行与出表没有形成清晰闭环。** `all` 串联评价、risk、path、external baselines、representation baselines、资源/身份/配对控制和 claims。旧 README、草稿和新审计记录不同步，用户需要自行识别实验版本才能判断结果。
6. **方法效果确有问题。** 最新 c591701 的 Full 在八个 city/budget 格均未胜过 Response-only。工程精简可以加快研究反馈，不能推断它会改善该结果。梯度摘要不足以定位原因。

重要纠正：当前 `_check_full_stage` 接受字段一致的科学 FAIL，并不因 G4/G5 为 FAIL 自动抛错。`_try_optional_stage` 等代码也已使部分早期阶段可选。不能重复把已放宽的门槛描述为现行硬阻断，也不能把所有异常全部吞掉。

## 最小论文范围

- 保留：固定数据划分上的跨城市定位，以及 Alignment/Response 对保留表征的作用。
- 正文表 1：四臂 CGS active AUROC、null 安全性、统一 Response probe NMSE、原生 Response NMSE；原生和统一探针不可混成同一指标。
- 正文表 2：四臂及相关外部基线在 Boston/Seattle、k=0/8/32/128 下的 Median/P90。明确 bank-macro 与 pooled 口径，不能直接换名字或混算。
- 附录：与保留主张直接相关的统计、配对/动作对照和计算量对照。交互与资源匹配仍是“协同/共享效率”主张的必要证据；如果不做，就收缩这些主张。
- 暂时移除风险概率、传播路径因果解释、第二引擎或真实域泛化主张，相应实验也不再作为核心出表前置条件。

## 新入口的目标形态

以下是拟议命令，不是仓库现有命令：

```text
train --config ... --arm ... --seed ... --resume ...
evaluate --run ... --task localization|alignment|response|controls
export-tables --runs ... --format csv,tex
```

每个任务有自己的 `PENDING/RUNNING/COMPLETE/ERROR` 状态；`hypothesis_supported` 是独立统计字段，不能作为写结果的条件。导出器输出已有数值、有效样本数和缺失原因，拒绝混用不兼容的划分/预算/协议，不填造假占位值。

## 实施顺序及完成标准

1. **先做现有结果的独立出表器。** 读取当前 localization summary/training summary/gate，按实验版本生成两类现有数值表；不依赖完整 Streaming 或 claims。标准：与当前 CSV 逐项一致，旧/新实验不能混入一张未注明的对比表。
2. **新建轻量 runner，不就地拆毁旧 runner。** 复用模型、损失、路由、统计；移除新路径的审批/环境闭包依赖，保存简单 manifest。标准：同一小型真实输入下与旧核心计算一致；真实 NPZ 尚不在此 clone，需要在数据所在主机验收。
3. **拆分 probe 和缓存。** 主能力任务不构建捷径大数组，单探针可恢复，按依赖复用特征。标准：中断后不重做已完成的优化更新；分别记录读取、编码、拟合、评分时间和峰值内存。
4. **取得同数据基线结果。** 统一定位划分与选择预算，保留各方法原生所需适配。标准：生成主表 2 的真实比较，含失败/缺失格与原因。
5. **方法研究。** 在源验证集比较联合损失/训练配方；通过多种子确认后冻结候选再做目标评估。新方案与旧方案分开标识，不能把既有目标结果当成无限调参反馈。最终仍以实际指标判断优势。

不承诺加速倍数、总工期或 SOTA。完成第 1–3 步的价值是把“无法得到表格”转化为可诊断、可恢复的实验任务，而不是自动得到正结果。
